# Дизайн-документ. Каталог персонажів

## Мета і межі

Консольний каталог дає змогу переглядати всіх персонажів, доступних у джерелі, відкривати їхні картки та створювати власні записи. Для віддалених даних використовується Genshin API й резервний доступ до даних його репозиторію. Власні персонажі зберігаються локально між запусками.

| Вимога | Очікуваний результат |
| --- | --- |
| Оновити список | `refresh` завантажує повний список ID від джерела, зберігає його та виводить разом із локальними записами. |
| Переглянути список | `list` показує віддалені ID і коди та імена власних персонажів. |
| Отримати інформацію й графіку | `show <id>` показує ім’я, опис, посилання на зображення, а за наявності також стихію, регіон, зброю й рідкість. |
| Створити персонажа | `create` запускає діалог із чотирма полями. Успішно створений запис одразу зберігається й отримує код із префіксом `user:`. |

## Структура додатка

| Модуль | Відповідальність |
| --- | --- |
| `__main__.py` | Розбирає параметр `--data-file`, створює адаптер API, сховище, сервіс і CLI. |
| `cli.py` та `commands.py` | Один цикл із запрошенням `catalog>`. Реєстр розбирає введення й викликає обробник. Обробники перевіряють аргументи, ведуть діалог і форматують вивід. |
| `service.py` | `CharacterCatalog` об’єднує віддалені та власні записи, перевіряє коди, оновлює кеш та координує збереження. |
| `model.py` | Незмінна модель `Character` з ID, іменем, описом, URL графіки та необов’язковими ігровими полями. |
| `genshin_api.py` | Повторно використаний HTTP-адаптер з об’єднаного проєкту гри. Отримує список та картки й перемикається на дані [репозиторію Genshin API](https://github.com/genshindev/api) при збої основного сервера. |
| `storage.py` | `JsonCatalogStore` читає й записує власні картки, отримані віддалені картки та останній список ID. |
| `portraits.py` | `PortraitCache` завантажує графіку та повторно використовує локальні файли. |
| `tests/` | Перевірки обробників CLI, відмови мережі, даних на диску й повторного запуску. |

Потік виконання: введення в терміналі → `CommandRegistry` → `CatalogCLI` → `CharacterCatalog` → HTTP-адаптер або JSON-сховище → відповідь у терміналі. Реєстр команд адаптовано з попередньої практичної, тому обробники мають спільний спосіб реєстрації, довідки й повідомлень про помилки.

## Реалізація консольного інтерфейсу

| Команда | Параметри та сценарій |
| --- | --- |
| `help` | Без аргументів. Виводить назви команд та їхні описи з реєстру. |
| `refresh` | Без аргументів. Отримує повний список віддалених ID, перевіряє результат, зберігає знімок і показує список. Якщо запит не вдався, доступний попередній знімок через `list`. |
| `list` | Без аргументів. Показує останній знімок і всі власні картки. Якщо віддалений список ще не завантажено, пропонує `refresh`. |
| `show <id>` | Приймає один ID, наприклад `amber` чи `user:star-keeper`. Власна картка читається зі сховища. Для віддаленої виконується запит, а у разі помилки видається раніше збережена картка з позначкою про локальну копію, якщо вона є. |
| `portrait <id>` | Повертає шлях до локального портрета й показує, чи його завантажено або взято з кешу. |
| `create` | Без аргументів. Запитує код, ім’я, опис і URL зображення. `/cancel` у будь-якому полі завершує діалог. Порожнє поле, хибний код, дублікат або некоректний HTTP(S) URL дають повідомлення про помилку. Після успішного запису виводиться збережений ID. |
| `exit` | Без аргументів. Завершує сеанс. EOF або Ctrl+C на запрошенні команди також завершує програму. |

Власний запис з кодом `amber` отримує ID `user:amber`. Віддалена картка з ID `amber` залишається доступною окремо. Картки друкуються в терміналі, а посилання можна відкрити у браузері.

## Дані та відмови

Файл зберігається в UTF-8. Типовий шлях `~/.character_catalog/catalog.json`. Параметр `--data-file` дозволяє використати окреме сховище для демонстрації. Версія 1 містить поля `remote_ids`, `remote_cards`, `custom_cards` і `source`. Кожне оновлення спочатку пишеться у тимчасовий файл, який замінює попередній файл після завершення запису. Пошкоджене сховище викликає помилку під час запуску. Типовий сценарій передбачає один активний сеанс на файл даних.

У разі недоступності основного сервера адаптер використовує віддалений список і JSON з репозиторію Genshin API. Після успішного `refresh` список доступний офлайн. Власні записи створюються й переглядаються офлайн. Графіка зберігається як URL, тому відкриття посилання залежить від доступності сторінки зображення.

## Перевірка

Запуск тестів: `python -m unittest discover -s tests -v`. Для демонстрації в терміналі виконати `refresh`, `list`, `show amber`, потім `create` та `show user:star-keeper`. Після виходу й нового запуску власна картка має бути доступною за тим самим ID.

## Бізнес-компонент. Парсинг даних для графічного інтерфейсу

`GenshinApi` виконує HTTP-запити й декодує JSON. `parser.py` приймає вже декодовані значення, перевіряє структуру й формує внутрішні моделі. `CharacterCatalog` викликає парсер та зберігає перевірену картку. Парсер можна тестувати окремо від мережі та консолі.

| Поля API | Поля картки | Обробка |
| --- | --- | --- |
| Список ID | `list_entries()` | Перевірка кодів, усунення повторів і сортування. Для підпису можна використовувати ім’я з кешу або ID. |
| `name`, `description`, `title`, `affiliation`, `birthday` | Однойменні поля | Ім’я обов’язкове. Для відсутнього опису є нейтральний текст. Дата зберігається у вигляді рядка джерела. |
| `vision`, `nation`, `weapon`, `rarity` | `element`, `nation`, `weapon`, `rarity` | Число рідкості зберігається як ціле або `null`. |
| `skillTalents`, `passiveTalents`, `constellations` | `skills`, `passives`, `constellations` | Масиви моделей `CharacterFeature` з іменем, описом, умовою відкриття, рівнем і типом за наявності. Відсутній масив стає порожнім. |
| ID персонажа | `image_url` | За ID формується посилання на графіку в репозиторії даних. |

Для списку майбутній інтерфейс викликає `catalog.list_entries()` та отримує записи з полями `id`, `label`, `origin`. Для вибраного запису `catalog.show(id)` повертає модель і прапорець використання кешу. Метод `card.to_view_data()` віддає незалежний словник, який можна серіалізувати в JSON. Масиви здібностей придатні для окремих секцій картки. Прапорець кешу можна показувати індикатором біля картки.

```python
entries = catalog.list_entries()
card, from_cache = catalog.show("amber")
view_data = card.to_view_data()
```

Некоректна картка відхиляється з повідомленням про проблемне поле. За наявності попередньої коректної копії застосунок повертає її. Старі JSON-збереження версії 1 завантажуються з порожніми додатковими полями та масивами. Власні картки й консольні команди сумісні з попередньою версією.

Поточний контракт охоплює список і картку персонажа. Таблиці покращень здібностей, костюми та матеріали залишаються в джерелі до появи окремих екранів для цих даних.

## Завантаження та кеш портретів

`portrait <id>` завантажує зображення за запитом і виводить абсолютний шлях до файла. Для віддаленого персонажа пріоритет має ресурс `portrait` у репозиторії Genshin API, резервним зображенням є `card`. Для власного персонажа використовується URL, введений під час створення. Якщо ID уже є у віддаленому списку чи кеші карток, завантаження графіки працює без повторного запиту JSON.

1. `CharacterCatalog.portrait(id)` визначає можливі URL і передає їх до `PortraitCache`.
2. Кеш шукає в папці `portraits/` поруч із `catalog.json` файл із назвою на основі SHA-256 URL. Для резервного URL теж перевіряється локальна копія. Під час влучання немає запиту зображення.
3. Якщо копії немає, кеш робить HTTP-запит з тайм-аутом, обмежує розмір до 10 МіБ і визначає розширення за сигнатурою даних. Підтримуються JPEG, PNG, WebP і GIF.
4. Дані спочатку записуються до тимчасового файла, тоді замінюють кінцевий файл. HTTP-помилки, неповні відповіді з відомою довжиною й помилки формату не створюють кінцевого файла.

Типовий шлях до кешу `~/.character_catalog/portraits/`. Параметр `--data-file` змінює місце JSON-сховища, і папка зображень створюється поряд із ним. Кеш зберігається між запусками й не має терміну дії. Для повторного завантаження можна видалити потрібний локальний файл. Зміна URL автоматично дає інший ключ кешу.

Майбутній графічний компонент викликає `path, from_cache = catalog.portrait(id)` і відкриває `path` локальним завантажувачем зображень. Збереження карток і бінарних портретів відбувається окремо. Тести перевіряють повторне використання після нового сеансу, резервний URL, помилки завантаження та файли з некоректною сигнатурою.
